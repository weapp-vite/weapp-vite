# off 模式的构建生命周期与发布依赖

## 证据与边界

Workspace HMR 的功能场景全部完成，但 `multi-platform-wevu-tdesign-demo` 的模板与脚本更新分别为 1555.4ms、1690.0ms，超过原有 1500ms 门槛。该应用使用 `sharedChunks: 'off'`。阶段指标包含并发调用与异步等待，不能把配置提取时间当作独占 CPU 耗时，也不能据此认定机器噪声。

代码中共享依赖图的维护与 `hasBuiltOnce` 状态推进同处于 `auto/full` 条件内。off 因此始终被当作首次构建：入口选择已收敛到变更页面，发布阶段却没有裁剪未变化的脚本。最小回归自然执行两轮 buildEnd、generateBundle 和 publication hook，第二轮仅改变 A，仍同时发布 app、A、B。报告的文件内容差异只有 A，不能证明 B 没有被重复写出。

## 实现选择

所有开发模式统一维护共享输出的 importer、依赖和源码映射，并通过现有构建生命周期进入增量发布。off 继续只决定入口重建策略：`buildStart` 可以登记受影响的共享 chunk，但不能据此把其他 importer 标为脏入口；原有入口选择层的 off 分支保留。

只推进 `hasBuiltOnce` 会让裁剪逻辑读取空共享图，删除当前页面需要的新共享模块。另建平行标志或在各处为 off 关闭裁剪，会继续保留生命周期与图状态之间的分歧，因此采用已有图与发布流程。

新共享模块可能继续引用第二层模块。发布计划中已确认保留的 chunk 都参与平台 API 等重写，不能只重写入口的直接 import。最终持久化继续由原生 bundler 负责。

## 回归与验收

`offLifecycle.test.ts` 使用真实模块图、构建与发布函数，验证首轮发布完整结果、次轮仅更新 A 而保留 B 的既有运行结果；第二场景让 A 首次引用共享模块及二跳依赖，执行最终发布代码并检查平台 API 重写。测试仅初始化首轮状态，不手动推进 `hasBuiltOnce`。

watch 策略回归比较 off、auto、full：三者均记录受影响 chunk，只有后两者通过共享图扩散 importer。相邻共享图、发布、类型检查与构建验证由统一串行回归执行，重建 dist 后继续检查相同应用与相同场景。原有目标、样本策略和性能门槛不变；局部测试不能替代正式全量验收。

本机验证完成：40 个相邻测试文件、523 项测试通过，`weapp-vite` 的 typecheck、test:types 与 build 通过。使用重建后的 dist 和 Node 24.14.1 对同一 TDesign 应用运行 nightly-full 定向诊断，原有两个场景均完成，模板与脚本更新分别为 507.0ms、513.9ms，P95 为 513.9ms，保留 1500ms 阈值且无超限。这些数值来自本机，不能与远端旧样本直接计算加速比例；完整远端矩阵和真实 IDE 验收仍待完成。

本次仅在现有大型生命周期文件中调整状态维护与策略边界，未迁移无关代码；拆分这些文件留给独立重构，避免扩大本次修复的验证范围。
