# 逻辑入口同步登记的真实路径复用

原资源门禁在最后一次 fresh build 的 create-server 阶段触及总期限。冷构建诊断显示，真实路径解析在整个 worker 中占有可观察的 CPU 权重；该诊断没有可验证的阶段时钟映射，因此不能把整份 CPU profile 当成 create-server 的阶段归因，也不能据此认定一个优化足以修复总期限失败。

最小反例使用真实配置服务和临时源文件，执行核心插件的 options hook。同一页面源文件在生成逻辑入口、登记 HMR 根节点、计算源相对路径时被解析三次；组件还计算物理输出路径，共解析四次。组件的源目录被解析两次。它们发生在异步 resolver 返回后的同一同步登记段。

实现只在该同步段复用已有 `withRealpathScope`。每个入口分别进入和退出作用域；resolver、扫描和文件存在性查询保持原有异步顺序。不扩大到整个 options hook，不跨入口、watch 批次或构建保留缓存，也不新增公开 API。成功结果在该操作内共享，失败解析仍由现有工具逐次执行并保留异常语义。

回归验证页面和组件的源文件各解析一次，组件源目录也解析一次，并保留逻辑入口、HMR 根节点和条目路径。异步 resolver 中途改向 junction 后，第二入口采用新目标；后续 options 调用重新读取 junction 和输出映射。登记 Map 的 Proxy 抛错时保留原始错误、不发布最终 input，已填充的路径作用域及时释放。已有工具回归继续覆盖递归作用域、失败后创建文件及异步 continuation。

options 源文件未超过 300 行，本次只修改既有登记段；不拆分 hook，避免为路径复用引入额外状态或改动原有加载顺序。

这项修改的直接结论是减少同步重复解析。原 512 个 SFC、14 次编辑、15 个步骤及总期限、性能和资源断言保持不变。包构建、下游 headless/真实 IDE 和正式资源门禁仍由总任务串行执行，只有这些结果完成后才能判断原问题是否解决。
