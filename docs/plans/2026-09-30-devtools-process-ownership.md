# DevTools E2E 进程归属与版本选择

启动失败和缓存恢复曾按名称终止所有微信开发者工具进程，Windows 使用镜像名、Unix 使用命令行子串。这会同时关闭手动打开的 IDE、其他项目和不同安装版本。自动恢复不能把进程名称当成资源所有权。

修复后的恢复只清理本次 bridge 启动明确登记的 CLI 子树。正常 close 与启动失败共享一次性 disposer；已退出的 bootstrap CLI 不向父进程报告可清理 PID。未知归属的残留 IDE 保持运行，不能自动误杀；需要重启时先确认实例归属并显式处理。

全局 session 与 port-lease 目录不再整体删除。会话自身的 close/disconnect、生命周期取消和桥接项目清理由原有资源管理器负责。

组件库 E2E 也不再扫描 DevTools 全部用户目录删除截图 PNG。文件名符合截图格式不代表本任务拥有它；旧实现会删除其他账号、其他项目的同格式文件。截图协议只返回图像数据，无法据此登记宿主临时文件的所有权，因此删除全局清理工具及 setup/会话轮换调用，仅保留仓库内测试输出目录和已登记进程资源的清理。宿主截图数量上限仍应作为真实失败报告，不能靠删除未知文件或弱化截图断言规避。

通过 `WEAPP_VITE_E2E_DEVTOOLS_CLI_PATH` 选择安装版本；显式传入 `cliPath` 优先，其次环境变量，最后使用原有平台默认值。登录预检、direct/bridge 启动与 engine build 使用同一解析入口。此环境变量只影响测试基础设施，不改变公开 CLI API。

平台默认值只是兼容路径，不负责识别安装渠道或查询最新版。实际 E2E 执行必须按下面的版本规则核验并显式选择，不能把路径 fallback 当作稳定版证明。

首轮修复曾保留缓存清理 API 的调用兼容性；后续完整 headless 验证证明全局缓存操作本身也越界，现已删除该 API 及所有调用，详见本文后续发现。恢复不会停止复用的手动 IDE，也不会猜测由 CLI 间接启动且无法确认归属的宿主进程。

验证包括跨平台清理回归、重复释放及失败后重试、CLI 选择和启动恢复测试；真实 IDE 验证需另外记录宿主版本、页面运行结果以及清理后进程是否仍存活。原生 WXSS 更新失败应保留为宿主/监听诊断，不能以进程存活替代样式验收。

## 固化的教训与执行规则

- 故障路径：E2E 启动失败进入自动恢复，Unix 按命令行名称匹配进程，Windows 按镜像名终止进程；同名进程包含手动实例、其他项目及另一安装渠道，扩大了清理范围。错误发生在资源所有权边界，不应增加更宽的进程匹配或重试来掩盖。
- 清理契约：仅释放当前任务登记且仍持有的 CLI 子树及会话资源。close、恢复、超时、取消和重试共用幂等释放；不复用已退出 PID，不删除全局 session、port-lease、用户缓存或登录信息。未知归属默认保留，其他活动测试等待完成。
- 回归门槛：模拟两平台的恢复入口，禁止全局命令和全局目录删除；真实子进程证明仅目标被释放；真实 IDE 检查恢复前后手动宿主和其他项目保留。进程仍活着不等于样式或 runtime 验收通过。
- 版本默认：每轮真实 IDE E2E 使用执行时官方最新稳定版，核对官方下载页稳定渠道、查询时间、所选安装和实际连接宿主。通过 `WEAPP_VITE_E2E_DEVTOOLS_CLI_PATH` 显式选择；记录实际 IDE 和基础库版本，不将本文历史探针版本永久设为“最新”。
- 版本例外：只有用户明确指定才使用 RC、nightly、开发版或旧稳定版。失败不能成为自行换版的理由；无法确认最新稳定版、未安装或未登录时保留证据并记录未完成，不静默回退，不绕过登录。既有固定目标的正式性能运行不重新采样。

这些规则同步到 `AGENTS.local.md`、生成 `AGENTS.md` 的源文档、公开 E2E skill 及其 checklist、网站 AI 工作流。后续审查清理代码和运行 E2E 时一并执行。


## 后续发现：共享缓存与 dev watcher 的同类边界问题

完整 headless 验证中，`lifecycle-compare` 在启动前仍调用真实 IDE 的 `cache --clean compile`。选择 runtime provider 只约束了 automator 启动，suite 前置操作绕过了该边界。此前只限制缓存种类为 compile 仍不安全：CLI 可能启动另一安装渠道的 IDE，且编译缓存也不是当前测试独占资源。另一个遗漏是 dev watcher 清理仍根据命令行匹配全部进程，同名或同路径不能证明所有权。

自动 E2E 不再提供或调用全局缓存清理 API。启动、恢复、suite 前置与 teardown 只释放登记的资源；headless 不读取或清理 IDE 状态。启动失败继续保留有次数上限的重连和项目就绪判断，失败时报告原错误，不用清缓存制造成功。Dev watcher 使用子进程句柄关联的幂等 disposer 登记，退出即撤销授权，Windows 同样清理自己的子树；重复 stop 和恢复不会重复释放，已退出 PID 不再被当作持有的资源。

回归覆盖 headless 不调用 IDE、没有持有资源时不扫描进程、不修改全局缓存或会话目录、同名非本任务进程保留、重复 close/cleanup 仅一次，以及退出后 PID 复用保护。清理不是环境修复授权；其他任务的活动 watcher 必须等待。

Performance Smoke 曾在进入测试前因性能脚本仍导入已删除的命令匹配清理函数而失败。已将该调用方统一到现有 `dev.stop()` 句柄清理，并加入真实 CLI 的 plan-only 入口回归，覆盖 ESM 依赖加载和场景发现。清理接口迁移需要检查脚本消费链，不能只搜索 E2E 目录；正确性冒烟也不代表正式性能门禁通过。

清理修复后的严格生命周期验收另发现 fixture 观测干扰：滚动回调更新日志预览，把日志面板高度从 55.5 增至 85.5，导致滚动参数在原生与 Wevu 页面间漂移。为日志面板预留固定空间，并增加记录前后布局不变的两 provider 检查；同时删除旧的 50 像素取整，保留实际滚动值比较。此修复只改变测试 fixture 的观测布局，不更改产品生命周期或宿主滚动语义。

完整 IDE 验收还暴露了 `agent-acceptance` 的启动所有权缺口：默认 10 秒的 `beforeAll` 超时后，原生项目仍在连接，Wevu 项目已开始启动。钩子超时不会取消异步 Promise；只清理已赋值的会话会漏掉迟到的连接。该 suite 现为构建和单次启动分别设置 60 秒与 90 秒预算，外层钩子保留 180 秒完成预算；teardown 等待已登记的启动 Promise 并关闭其会话，启动失败仍由 setup 保留原始错误。回归测试复现旧代码提前完成 teardown，修复后等待并关闭迟到会话。系统锁屏是本轮另一个已确认的环境限制，调整生命周期不代表真实 IDE 全套已通过。

完整 CI 验证时，父进程显式设置 CLI 路径又暴露了测试隔离遗漏：启动恢复的 mock suite 继承该值，却有五个断言要求平台默认路径。现在默认路径契约在每个用例内隔离该环境变量，结束后恢复原值；显式选择用例另行设置测试 CLI，并验证登录、预构建与 direct 启动共用该选择。此处不改变真实 E2E 的路径优先级，也不靠取消稳定版显式选择来使测试通过。

脚本入口也属于审查范围。分包场景轮播曾在每次切换后用应用级退出和进程名称匹配终止整个 IDE；两个最小回归确认每轮 11 个场景额外发出 44 次全局操作。轮播没有宿主独占所有权，现在只打开目标项目并保留现有窗口。打开场景必须显式选择本轮核验过的 CLI，直接执行有超时边界的项目 open，失败原样报告，不经过全局关闭或重启恢复。纯构建场景无需 IDE。六个 mock 单测覆盖手动/自动轮播、失败保留、版本选择和无隐式回退，不替代真实 IDE 验收。


三系统契约 CI 后续发现退出与日志完成的边界：原生进程已有 exitCode 时不能再终止旧 PID，但 execa 仍可能排空最后一段输出。`stop()` 现在撤销终止权限后有界等待退出 Promise，确保最终诊断能被观察；发送每一个 SIGTERM/SIGKILL 前也再次检查原句柄仍持有，避免根进程退出后按旧快照强杀。两个定向文件在原实现上 3 项失败、6 项通过，修复后 9 项通过，包含延迟输出、旧进程树失去归属及幂等清理。

Windows 独有的两个超时来自测试只模拟 `ps`，却让 Windows 走 `taskkill` 后等待未完成的 mock Promise。Unix 进程发现契约现显式选择模拟平台，并增加 Windows 仅按持有 PID 清理一次的覆盖；不靠延长测试 timeout 掩盖平台差异。

本轮定向复验后，使用与 CI 一致的 `pnpm vitest run -c e2e/vitest.e2e.internal.config.ts --maxWorkers=1 --no-file-parallelism` 串行执行完整 internal contracts：79 文件、743 项全部通过。测试期间没有并发 E2E/watch；这是基础设施契约验证，不是新的真实 IDE 通过证据。
