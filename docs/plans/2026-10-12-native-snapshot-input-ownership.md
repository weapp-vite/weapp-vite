# 原生脚本与资产快照的输入归属

## 复现与证据

议题 #1134 的原四文件断言曾出现模板、样式、JSON 已更新而脚本仍旧。随后绿色运行中的脚本通知均早于资产通知，不能解释首次失败。

一次私有自然时序探针在父进程收到首个真实侧车通知后保存脚本，不改变 40ms debounce、120ms polling 或原 30 秒断言。独立快照的实际 JS bundle 已包含新 marker，收尾 bundle hash 与 snapshot-ready 一致；三个侧车成功写出后，JS 通知和 JS-only delivery 才到达，随后发布 delta，磁盘 JS 仍保留旧 marker。原四文件断言失败，完整时序与首次失败分别保留。

## 所有权选择

资产快照读取文件早于活动 DevEngine 接收监听通知。仅凭 `unpersistedNativeScripts` 的事件集合无法说明快照究竟消费了哪个脚本版本。增加私有输入记录，在编译器返回实际原生源码字符串的边界记录版本；覆盖固定输入与文件读取，不以构建完成后的磁盘读取代替实际编译输入。

成功提交的资产保留本次实际原生输入版本。真实 JS 通知到达后，如果资产已经消费了不同于已持久化脚本的版本，沿现有完整发布路径同步文件；资产稳定后才发生的独立脚本编辑没有这种版本差异，继续 delta。独立 compiler delivery 的快照提交也核对已经收到的脚本通知，避免通知先于资产 adopt 时丢失完整发布要求。

不在通知到达前主动要求原生引擎读取尚未失效的模块图，不补发 watcher 事件，不扩大 polling 或 debounce，也不手写最终 bundle。完整发布成功后推进脚本基线，失败、被取代及写入期间的新版本分别保留原所有权。

## 回归与完成边界

新增运行时用例先从首次构建的基线执行，再通过完整四文件保存、成功发布和页面观测恢复基线，避免既有脚本补丁的未持久化状态掩盖迟到通知。确定性单测覆盖实际输入、通知和提交的先后顺序，以及固定源码、失败、被取代、恢复与独立脚本补丁。实际快照构建验证记录的是编译输入而非后续磁盘内容。provider-compatible runtime 使用原 native-batch fixture，在首个真实侧车通知后只保存一次脚本，继续检查四文件、构建身份、页面数据、节点文本及真实 IDE 计算样式。

现有 fixture 页面、真实 AppID 和页面条件保持适用；suite manifest 必须继续在严格 headless 与正式 IDE 清单包含该文件。先完成包级检查，重建 dist，再串行执行下游。本轮所属包 223 个测试和其余 stateful 323 个测试通过，包级 typecheck、公开类型测试及范围 ESLint 通过。重建后的三个 headless 四文件用例均通过，完整 trace 确认资产提交后 JS 通知才到达，随后完整发布成功；资源与机器租约均已释放。真实 Stable IDE 仍有独立启动限制，未经最终验收不能关闭 issue。

既有 `session.ts`、`snapshotBuild.integration.test.ts`、`session.snapshots.test.ts` 与 build service 超过 300 行。本次使用私有输入记录模块并沿现有输入、资产提交、原生发布边界接入；不在本修复中拆分整套状态机，以免扩大生命周期变更范围。
