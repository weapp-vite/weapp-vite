# Windows classic IDE 配置锁回收竞争

原生 Windows Node 22 验证中，两个回收者同时删除同一已死亡持有者的 token 时出现 `unlink EPERM`；同轮 Node 24 通过。已有修复只覆盖发布候选目录时的重命名竞争，未覆盖 token 删除竞争。日志未直接证明 Windows 底层删除状态。

只对已通过 `ESRCH` 确认死亡的持有者，重试观察到的精确 token 路径。重试与候选发布共用原有绝对截止时间，每次等待不超过剩余预算；`ENOENT` 表示旧 token 已被另一回收者处理。预算耗尽保留原始 `EPERM`，其他删除错误立即保留。正常持有者释放不重试，目录清理与所有权协议保持原有约束。

直接忽略 `EPERM` 会掩盖持续权限错误；删除整个 guard 会危及替换持有者；为删除阶段另设预算会延长事务等待。采用原预算内的精确 token 重试，不要求用户修改系统配置。

新增确定性回归覆盖瞬态与持续冲突、共享预算、替换持有者、正常释放及其他权限错误。保留原生双回收者竞争，区分初始参与者与重试次数，并等待两个调用均终结后再清理 fixture。新增用例单独存放，避免原测试文件超过 300 行，也不引入跨文件共享 mock 状态。

验证顺序为新增回归在原实现上复现失败、修复后锁及相邻配置回归、最小 ESLint、所属包类型检查与重建、当前提交的原生 Windows 矩阵，以及后续 headless 和真实 IDE 验收。原始失败与旧提交的完整 E2E 结果保留各自身份。

后续原生 Windows Node 24 验证暴露了另一处竞争：普通并发事务在读取持有者 token 时收到 `open EPERM`。进程启动和目录发布已完成，现有读取直接将它包装为不可接管错误。日志不能确定底层句柄状态，因此不将该错误解释为记录不存在或持有者死亡。

读取只在获取锁期间、原绝对截止时间内重试原生 `EPERM`，每次从目录枚举开始重新读取和校验，避免重试旧文件路径而遗漏替换持有者。获取阶段删除空目录后的权限回读同样传递该截止时间。持续拒绝访问保留最后实际错误作为原因；其他权限错误、损坏内容和未知格式立即拒绝。正常释放不传递重试预算，保持即时错误行为。

忽略读取错误会失去所有权依据，只重试旧 token 会错过替换记录，另设读取预算会延长事务等待。采用完整回读并复用原预算，新增独立测试覆盖瞬态读取、消失与替换记录、持续拒绝、共享预算、损坏记录及释放边界。源码与新测试均未超过 300 行，无需继续拆分。
