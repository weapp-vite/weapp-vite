# IDE 项目窗口回收

本轮全量回归出现多个测试项目窗口残留，持续占用模拟器内存和 CPU。用户强制退出 IDE 后，先修复资源生命周期，再恢复验收。验收版本仍为用户指定的 Stable `2.02.2608070`，官方版本查询及显式版本例外报告保持不变。

## 根因

连接断开只释放 WebSocket，不能证明项目窗口关闭。启动失败、迟到连接及 worker 退出都可能发生在窗口已经打开之后。日志收尾曾用同一状态阻止后续 `close()`，父任务又没有窗口所有权记录，因此窗口会跨 suite 累积。

## 实现边界

- 受管测试使用所选安装的官方 `agent start`，依据 `openedProjectWindow` 区分新建和复用。直接项目及 HMR 保留原项目目录语义。
- 启动前向任务专属 journal 写入 intent。只有确认新建并核验宿主身份后才授予关闭权；缺失回执不能靠路径猜测所有权。
- 窗口所有权独立于连接状态，记录安装、项目、端口、监听进程 PID 与启动身份。监听进程可能是 IDE 后端，不能冒充窗口身份。关闭前复核身份，通过精确 `close --project` 请求后，等待本次窗口实际销毁及所属端口释放。
- 已释放记录不能再次关闭同路径；复用的手动窗口不属于任务。失败清理保留记录、允许重试。
- worker 和父任务均执行收尾。任何未确认资源或清理失败停止后续任务，包括允许收集普通测试失败的模式。
- 同一任务的各次启动共享显式登记的 journal 作用域。检查历史失败与登记新启动使用同一把根锁；即使调用方吞掉关窗异常、改用另一份子 journal，也不能绕过尚未完成的启动或清理。已确认的健康窗口占用根作用域额度，默认最多一个；共享宿主、并发会话和生命周期验收显式声明两个窗口时才允许另一项目并存，回收仍只作用于明确传入的子树。
- 常规公共共享连接仍保持原有连接语义，受管行为由任务显式环境启用。
- `dev --open`、HTTP 打开和 engine build 共用受管入口，不能先开窗再把自己的窗口误认成借用窗口。受管打开失败向调用方传播，不继续回退或启动构建恢复。
- 没有本轮精确关闭请求证据时，后端退出或端口消失不记为窗口已关闭。关闭发送意图在 CLI 执行前落盘；已发送但结果未知、或销毁迟到时，重试只继续观察，避免再次关闭同一路径。

## 当前版本的窗口销毁证据

本轮核对的 Stable `2.02.2608070` 中，官方 `close` 返回成功只表示关闭请求已交给窗口服务。项目后端和 automator 端口先退出，原生窗口可能随后由宿主的关闭回调销毁。宿主内部的 3 秒 fallback 计时器可以取消或延迟，不能用固定等待时间判定完成。官方 CLI、HTTP 和 MCP 接口没有提供可替代的窗口销毁完成查询：项目列表返回导入项目，runtime 查询依赖已退出的后端。

受管关闭使用 `wechat-devtools-window-close-trace-v1` 记录本轮实测的主进程日志协议。关闭前只读取所选安装 `profileDir/WeappLog/logs`。macOS 且具有已登记宿主身份时，通过下述活动文件描述符规则选择日志；其他平台或无 host 时保持原捕获路径，在捕获的文件长度内逐行确认所选产品版本和 `MAIN` 来源，并要求唯一完整 MAIN 流。两条路径均保存文件身份、字节游标和游标前的内容摘要，不扫描其他安装，也不按文件日期选择最新候选。日志来源必须位于完整行的开头，消息体内的标记及尚未换行的尾部不参与识别。扫描使用分块读取和有限的行首缓冲，不将整个日志载入内存。原捕获路径的绑定证明日志来源，不将它表述为主进程 PID 绑定。游标之前的日志与未完成旧行都不能成为本次销毁证据。CLI 执行前先持久化发送意图，每次读取新增完整行后再持久化游标和已关联的窗口身份，父任务可以继续观察同一次关闭。

新增日志必须来自所选产品版本，并按以下证据关联：`native-close-call` 的 `winId`、`browserWindowId`，以及 `close-requested` 的准确项目路径、`runtimeId`。只有同一日志文件和窗口身份的 `native-window-closed`、`webcontents-destroyed`（`destroyed: true`）均出现，且 automator 端口已释放，才能将记录标为 `released`。CLI 回执在 worker 退出前未落盘时，也必须通过这组实际销毁证据完成恢复，不能重复发送关闭命令。

无法选择日志流，或选定文件缺失、截断、替换、轮转、版本变化、关闭取消、窗口关联歧义时，都保留失败记录并阻断后续任务。同一文件中新出现主进程启动标记也视为代际变化。超时仅表示尚未得到完整证据，允许下次从原游标继续观察。日志协议是本版本的验收依据，不视为微信公开稳定 API；版本升级或日志协议变化需重新验证，不能回退为仅检查端口或固定延时。

真实取消回归发现该目录的辅助日志会变化。所选 IDE 的 FileTransport 最多保留 30 份文件，新增文件会按创建时间淘汰旧文件；本次新增文件监听日志淘汰了一份关闭前已为空的历史日志。原 MAIN 的身份、锚点和完整窗口销毁链均未改变，因此不能把整个目录集合相等作为关窗的完成条件。后续只续读已固定的日志游标，无关日志增删不参与判定，新建文件不能补充证据。已捕获日志删除或发生 10 MiB 轮转仍是证据边界，当前实现保持阻断，不宣称能够跨日志流恢复。

完整真实回归还发现：MAIN 自身日志与转发的 BACKEND、PROJECT 日志共用同一 FileTransport。旧的活动日志被共享保留策略移除后，主日志服务会创建新文件，其首行可以属于 BACKEND，后续才出现 MAIN。实测失败中的新文件第 132 行出现 MAIN，关闭前按首行选择会错误地得到零候选。识别完整行修正了这一文件格式假设，但还不能证明找到的是当前活动日志。

2026-10-06 的诊断轮进一步确认了零 MAIN 的边界：逐行扫描当时全部 30 份日志后，所选版本没有任何 MAIN 记录。共享 FileTransport 会删除其他进程仍打开的旧文件；主日志服务发现原路径消失后创建新文件，并先写入转发的 BACKEND、PROJECT 消息。已核验主进程当时持有唯一仍有目录链接的可写新日志，设备号和 inode 与现存文件一致，另一个历史描述符指向已 unlink 的文件。要求关闭前必须已有 MAIN 内容，会阻止产生下一条 MAIN 关闭记录的请求。这是日志流选择的前置条件错误，不能据此认定窗口已经关闭。

选择规则还必须处理关闭前已经完成的 10 MiB 轮转：历史文件可能仍是目录中唯一含 MAIN 的文件，主进程却已经写入另一份新文件。因此不能只在零 MAIN 时尝试活动描述符绑定，也不能把历史 MAIN 唯一性当作当前写入目标的证明。

正常重启宿主后的真实 worker 回收还暴露了多日志边界：同一主进程同时持有两份有目录链接的可写日志，其中一份非空，另一份为空。所选安装同时初始化现代 `MainLogService` 与旧日志模块的 `FileTransport`；旧模块会预先创建空文件，并有后续注册 transport 的调用。因此“一个主进程只有一份可写日志”的假设不成立，空文件也不能直接排除。该轮 worker 已完成首次就绪并被强制终止，失败发生在父任务选择关闭证据源时，区别于此前模拟器首次启动失败。

macOS 且 journal 具有宿主身份时，修复使用活动描述符集合：重新核验 backend 的 PID、启动身份和可执行路径，通过父进程关系核验所选安装内准确的 Electron 主可执行路径及启动身份，再检查该主进程当前打开的文件描述符。候选必须是所选 profile 的规范化日志目录内、可写、仍有目录链接的常规 `.log` 文件；排除符号链接，使用设备号和 inode 将描述符、路径与实际打开文件绑定。第一次枚举后捕获全部文件游标，再做第二次枚举并复核宿主身份；两次完整描述符集合必须一致，文件正常增长和枚举顺序不影响比较。多个描述符指向同名、同 inode 时只读取一份物理文件；重复描述符或同 inode 对应不同路径仍拒绝。明确已 unlink 的历史描述符不计入候选；其他无法核实的状态继续阻断。不按是否为空、是否已有 MAIN 内容、名称或修改时间选择某一份。父进程关系只用于定位证据源，不授予关闭或终止共享主进程的权限。

该路径把核验的主进程身份作为 `mainHost` 与全部原文件游标一同写入 journal，每次等待续读前验证身份。项目关闭后 backend 可以正常退出，恢复直接使用已登记的 `mainHost` 和日志集合，不重新查找父链，也不从同路径的新 backend 获取身份。捕获之后仍固定各文件的 inode、offset 和 anchor；替换、删除或无法衔接的轮转不能迁移到另一日志，即使另一文件由同一主进程打开也不例外。关闭请求、原生窗口关闭与 WebContents 销毁必须在同一 `fileIdentity` 中完整关联；不同流不能拼接证据，另一流出现同一项目的第二个关闭请求继续拒绝。宣布成功前须检查所有固定候选在本轮已观测边界内的完整行，不能因一份日志先出现完整证据而漏掉另一份日志积压的冲突。等待期间不增补新描述符或文件；这不等于持续检测主进程全部描述符的变化。

macOS 的进程身份或描述符核验失败时，不退回历史 MAIN 扫描。其他平台或无 host 时仍要求唯一完整 MAIN，零候选或多个候选均拒绝。活动描述符路径只纳入同一已核验主进程持有的固定文件集合，不依赖历史 MAIN 的数量，也不扩大为读取整个 profile 的日志。文件名日期、修改时间或任意 BACKEND 内容都不能替代进程和文件身份。

旧版本因目录集合变化留下的失败，只允许在原游标内重新验证后收窄为唯一 MAIN。原非空文件必须保留身份、偏移和锚点；已丢失文件只有原偏移为零、空内容摘要且没有未完成旧行时才能排除。用于识别的完整 MAIN 行必须位于原偏移之前，已有调用和窗口关联必须全部来自该原文件。恢复会持久化原失败与全部旧游标，再从原偏移续读，不重新捕获偏移或重复发出关闭命令。其他永久失败不经过这个兼容分支。

## 中断与外层入口

suite、命令序列和防休眠入口共用可重复触发的信号作用域。第一次 `SIGINT` 或 `SIGTERM` 开始收尾，后续信号不越过清理流程；退出时仅移除当前入口安装的处理函数。中断报告保留已执行任务，不继续下一项。

外层命令持有自己的项目 journal 和机器租约。Unix 关停会核实本次创建的进程组，而不只等待直接子进程退出；内层 suite 的 5 秒关停期限包含在外层 10 秒期限内。正常退出立即结束等待，只有仍活跃的本任务进程才进入强制终止。Windows 的进程树终止无法确认时保留记录并停止验收，不把主进程消失作为后代已退出的证据。

每条外层命令和每个 suite 任务获得独立的机器租约子作用域。派生凭证保留完整祖先链，登记借用者与封存作用域使用同一个变更锁。父任务先封存入口、拒绝迟到登记，再核实子树没有活跃借用者，随后回收自己的项目 journal。进程停止或窗口回收未确认时，未完成状态阻止根租约释放和后续运行接管。祖先作用域不能覆盖后代尚未确认的停止状态，也不能将外层进程组退出当作独立子任务已停止的证据。

嵌套 runner 被强制终止时，可能来不及封存其任务作用域。仍存活的父任务通过显式后代恢复入口接管：先封存父入口并核对整棵登记子树，确认其中没有活跃借用者；再按后代优先顺序，使用创建 scope 时绑定的 `cleanupKey` 调用清理。E2E 的 key 是提前创建的任务 journal，必须位于父 journal 的准确 `children` 链中，并持有同一根作用域标记。回调实际回收资源、核验全部记录已释放后，才可完成该后代。回调前后均比对登记快照；未知记录、存活进程、缺失绑定或清理失败继续阻断。该入口不改变普通 `seal`、`complete` 对未完成后代的严格检查，也不自动接管旧的无绑定 scope。

入口先创建 journal，再分配命令 scope，避免 journal 初始化失败留下永远未发布的 scope。回调与机器租约释放同时失败时，保留两项错误及原始原因，便于区分任务故障和未完成回收。

若外层进程已退出而封存作用域尚未完成，普通入口仍拒绝接管。显式恢复入口要求调用方提供原 owner、全部 scope 和 borrower 的精确快照，并逐项验证登记完整、作用域已封存、原 owner 与所有借用进程均已退出。恢复在同一变更锁中保留原快照审计，更新恢复进程的租约身份，但不预先完成任何 scope。调用方按后代优先顺序回收各 scope 对应的明确任务 journal，验证资源均已释放后才完成 scope；失败继续保留租约与 journal。该入口不推测未知 journal，不将进程退出视为窗口退出。

恢复写入期间崩溃时，短变更锁和审计仍会阻止普通接管，需要继续核对精确状态；这不是自动清除遗留锁的入口。已成功恢复的旧快照不能用于第二次接管。

独立生命周期脚本也通过该外层命令执行。公开入口启动受管的内部 `--run`，后者和 `--worker` 都必须在运行场景前通过继承租约校验并取得明确的项目 journal。内部场景结束后，外层仍等待进程停止、窗口回收和 scope 完成；内部清理失败不能通过返回错误后释放根租约来绕过阻断。故意被 `SIGKILL` 的 worker 直接执行场景，保持原有被测语义，不再额外创建必须由它自己完成的 machine scope。

关停回归包含真实子进程：直接父进程先退出、后代忽略终止信号，以及外层命令经 suiteRunner 启动独立任务组的取消流程。模拟时钟测试单独控制计时器，运行时关停期限保持原值，不通过放宽普通测试超时掩盖残留。

## 验证

先用聚焦回归验证断连后关闭、失败重试、重复关闭、宿主及端口身份变化、复用窗口保护、worker 异常退出和父任务停止规则。重建受影响包后，以少量真实窗口验证连续启动和回收，核对窗口及进程资源回到基线，再运行全量回归。真实结果、SDK 版本和 journal 随本轮验收记录保存。

活动描述符选择需补充临时 profile 回归，覆盖旧文件 unlink、新文件仅有 BACKEND、PROJECT、历史已 unlink 描述符、轮转后历史唯一 MAIN 已非活动流，以及错误安装、profile、主进程、多份有效日志、只读文件、符号链接和设备号或 inode 不匹配。多流回归须覆盖空流与非空流、枚举排序变化、捕获期间集合变化、硬链接路径歧义、跨文件销毁事件、积压内容中的第二个匹配请求和多游标序列化恢复。还需覆盖 journal 恢复时 backend 已退出、`mainHost` 身份变化、捕获后轮转，以及其他平台或无 host 的原有严格选择规则。上述根因来自只读进程、日志与安装源码调查；本段记录修复边界，不代表聚焦测试或真实窗口恢复已经通过。完成包级验证并重建后，主任务仍须通过正常 ownership 恢复入口核验实际双销毁证据、端口释放及作用域和机器租约收尾。

2026-10-06 完成该修复的首轮验证：活动文件描述符模块 48 项回归、CLI 包 787 项测试、类型检查、公开类型契约、构建和改动范围 lint 均通过。随后使用原失败记录的精确快照恢复唯一遗留窗口，记录到本次关闭请求、原生窗口销毁、WebContents 销毁和端口关闭；两个未完成作用域正常收尾，机器租约释放。共享宿主及原有项目进程身份保持一致，重复清理没有再次发出关闭请求。该结果证明本次遗留窗口已回收；完整生命周期与全量 IDE 验收仍需继续，锁屏期间的界面复核尚未完成。

同日正常重启后发现的双 transport 问题另补了多流回归。修复后的 CLI 包 818 项测试、类型检查、公开类型契约、构建和改动范围 lint 通过；从原失败报告与租约的精确快照调用正常恢复入口，固定两份原日志后取得同一窗口的完整双销毁证据，端口关闭、未完成作用域收尾与重复清理均已核验，原有七个共享宿主进程身份保持不变，Computer Use 确认返回项目列表。该结果证明此遗留窗口已回收，不替代完整十六步生命周期或 full/exhaustive 验收；原失败报告保持不变。
