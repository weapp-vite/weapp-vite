# Stable 宿主与安装边界

## 根因与设计

原来的全局 CLI 配置、E2E 显式 CLI、按更新时间发现的 profile 端口和仅按项目缓存的自动化会话各自决定目标。同一 macOS 用户下的 DevTools 还共用 Electron 单实例锁；启动另一安装可能把命令交给现有宿主。已观察到上述本地选择冲突，不能仅据此断言微信服务端踢掉了账号。

本次让一次操作只解析一个安装上下文：canonical CLI、应用资源路径、安装标识、产品版本、渠道和 profile。版本读取应用 package.json / ASAR 元数据，不读取外层 Electron 版本。未绑定上下文时，显式参数优先于进程 `WEAPP_IDE_CLI_PATH`，再到用户配置和平台默认；已绑定 `target` 时，冲突的 `cliPath` 明确报错，相同 canonical 路径的别名仍可使用。公共库保留显式选择其他渠道的能力；仓库真实 IDE 验收要求 `WEAPP_VITE_E2E_DEVTOOLS_CLI_PATH`，核对官方最新 Stable，并向子调用传递本轮选择，不修改全局配置。

HTTP 端口发现只访问所选 profile，运行时端口、持久会话、共享连接和 MCP 缓存包含安装身份。连接前核对端口监听进程；显式端口也不例外。端口必须为 1–65535 的整数，CLI 和 REST 不截断小数或带杂字符的输入，不把非法值降级成默认端口。旧记录或未知归属不直接复用、不删除。构建开始、轮询、HTTP 到 CLI 的外层回退和恢复都保留原 target。

真实窗口恢复还暴露了 HTTP 打开接口的历史参数错误：现代 `/v2/open` 使用 `project`，旧 `projectpath` 会返回空对象但没有打开目标项目。现使用单次 URL 编码传递 `project`，并将空正文或空对象标记为未确认；有响应仍需结合项目会话或原生界面验证。

同机同用户的 E2E 使用固定用户状态目录中的目录租约，覆盖 suite、直接 Vitest、脚本及多命令聚合入口。子进程需验证父持有者 PID/token 后登记借用；孤儿子进程仍活跃时不可回收。释放验证归属且幂等；未知记录保守保留。AsyncLocalStorage 区分同一异步链的嵌套操作与无关并发调用，环境引用计数保证子调用完成前凭证不被提前撤销。现有项目租约、端口租约及一个 suite 中多会话能力保留。

共享登录指多个项目复用同一个已登录宿主。没有复制账号票据、同步两个安装的凭据、退出账号或清理全局缓存。正常账号过期仍需通过官方登录流程处理。headless 不解析 IDE 安装或访问登录状态。

新增的公开共享会话验收同时发现 headless adapter 缺少 `disconnect()`：页面导航已成功，释放连接时却无法关闭所属 runtime。现由既有 adapter 提供同步、幂等的 `disconnect()`，异步 `close()` 复用它，正常释放和取消后的迟到清理使用同一生命周期契约。

## 代码组织

安装解析分为 metadata、profile 和 host 检查模块；自动化模块拆出安装上下文、会话存储和错误分类，主编排缩短到约 180 行。现有超过 300 行的 engine、运行时 session manager、wechat-commands 与 E2E automator 文件只接入统一上下文或租约，保留原生命周期与公共命令编排边界，避免将无关重构混入行为修复。
