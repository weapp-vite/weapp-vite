# HMR 失败现场的观察边界

## 原生样式

议题 #1081 的历史失败已经证明最终 WXSS 含目标规则、客户端确认脚本；这些结果不能证明原生页面加载了该规则。同一轮缺少实际节点 class 与匹配规则，尚不能区分类名不匹配、旧样式缓存和样式作用域问题。

Stable 2.02.2608080 的基础库 3.17.3 静态协议实现支持 `CSS.getMatchedStylesForNode`，由实际渲染后端取得规则；`CSS.getStyleSheetText` 未实现。因此采用失败现场的匹配规则查询，不把磁盘 CSS 当成已加载 stylesheet，也不新增公共 API。

事务测试只在原断言失败后读取原生当前页面、目标节点 class、计算颜色和匹配规则，并分别记录已写出 WXSS 的 SHA。Element 命令先校验页面仍为原生栈顶，CSS 查询沿用该页的 DOM 节点 ID；页面或节点身份不可读时不猜测 nodeId，两项页面身份校验均失败时不查询可能属于其他页面的 CSS。每条协议读取有独立短超时，记录观察起止时间，不宣称多条读取构成原子快照。

协议、文件或报告写入失败只记录诊断缺口，不覆盖原始断言。没有新增导航、编译、重载、重试或样式修改，也没有使用 `setStyleTexts` 等写接口。纯单测验证页面校验顺序、磁盘和匹配规则观察面分离、协议缺失及报告写入失败。真实 SDK 能力和原样式断言仍须在实际运行中验收。

## Windows 进程查询

历史 CIM 超时有两种现场：已收到 query begin，但未收到 query end；或者没有收到脚本标记。旧版首标记在 UTF-8 设置之后，后者不能证明 PowerShell 没有启动；query 区间也包含模块加载、查询及字段投影，不能仅凭该标记归因为 CIM provider。

诊断启用时使用 V2 标记：script begin 位于 UTF-8 设置前，补充 UTF-8 begin/end，后续查询与序列化仍各有边界。兼容 V1 的原六阶段时钟，报告明确记录 markerVersion，不混合不同版本的时间。诊断关闭时命令保持不变。

Node 侧旁路观察同一个 Execa 子进程句柄，记录 handle、spawn、error、exit、close 及首次 stdout/stderr 的单调时间和 PID。日志不包含命令、路径、错误消息或输出正文。每事件最多记录一次；Execa 结算时移除临时监听，close 的一次性监听可稍后收到，不等待它延后正式结果。

保留原单次完整 CIM 查询、身份字段、10 秒预算及所有权门禁，不预热、不重试、不扩大清理范围。纯单测及短生命周期 Node 子进程只验证观察器本身；它们不能代替 Windows 上的原查询验收，也不能证明历史超时的根因已经修复。
