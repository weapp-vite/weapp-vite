# 基准失败与进程清理证据

Nightly Performance 运行 `38015096276` 的 Windows auto-import HMR 分片在首个 baseline 配置收尾时，进程树查询超过既有十秒预算。原始错误已保存，存活 dev 进程让外层 collector 继续等待，最终在十五分钟期限失败。该证据只证明清理查询失败，不能证明此前采样一定失败，也不能唯一归因于 CIM。

现有清理器在首次快照失败后没有完整后代清单。如果根进程随后退出，重试不能把未知后代当作空集合。保存首次失败原因；根仍由原句柄持有时允许重新核验，捕获包含原根身份且已知候选全部对账后才撤销未完成状态。根在异步查询期间退出，或已知候选在重查时消失，都不能证明此前未知后代已退出。根已退出且此前捕获失败时持续拒绝完成，不再按旧 PID 发现进程树。已成功捕获的身份及已知候选仍遵循原有退出、换代和精确终止契约。

自动导入基准复用现有 `runWithCleanup`，同时保留采样与 dev 收尾错误。只有 dev 收尾完成才删除临时项目；删除失败与正文首错一并保留。`error.txt` 复用现有错误序列化器保存 JSON，保留 cause、聚合子错顺序与非 Error 拒绝消息，避免只有通用聚合错误名称。失败运行仍无有效验收结论，不更改采样合同、查询预算、性能阈值、身份比较或终止权限。

回归首先证明旧清理器在“快照失败、根退出、再次 stop”时错误返回成功，再验证修复后重复拒绝且保留原 cause；另验证两条异步退出竞争和根仍持有时完整重查可以恢复。基准回归执行真实脚本入口，检查正文与清理同时失败、未回收项目保留、目录删除失败、非 Error 拒绝、错误文件及正常清理顺序。本地 mock 与受控子进程结果只证明这些内部契约，不代表 Windows 原查询超时或真实 IDE HMR 已修复。

自动导入基准主脚本超过三百行，本轮只调整既有测量闭包的生命周期包装；不搬迁采样逻辑，避免改变性能观察边界。清理状态仍由独立 `devProcessCleanup` 模块负责。

模板基准另有明确的清理契约缺口：吞掉 `dev.stop()` 拒绝后仍删除 workspace、返回成功结果并继续下一个模板。Windows classic TDesign 分片的报告失败数为零、外层随后等待到期限，但缺少 stop 拒绝或存活句柄记录，不能将此源码缺口称为该次挂起的确定根因。修复只改变清理失败路径：失败向入口传播，保留正文与收尾错误、dev 日志及未回收的 workspace，停止后续启动和成功样本发布。普通采样错误在收尾成功时保持既有失败结果报告策略。

模板清理失败快照保存到 `failures/<template>/cleanup/report.json`，与场景 `<scenario>.json` 分开命名，保留已有场景结果、诊断、样本和完整聚合错误链。逐字段脱敏后再生成 JSON，覆盖 Windows 路径、凭据、换行和引号；快照写出失败与原收尾错误一并抛出。真实脚本入口回归同时验证采样失败与 stop 失败、证据保存失败、同名场景不覆盖，以及正常采样结果报告策略。

扩大定向 TypeScript 检查到模板基准入口后，传递依赖中的 `template-e2e.utils`、`automator` 和 `managedAutomatorBridge` 共报告十四条已有类型错误。干净 `main` 提交 `e77123f98` 的对照日志与修复树逐字一致，不能把该检查记为通过；所属 package 的 typecheck 与类型契约检查独立通过。旧错误涉及跨 provider 的连接返回类型等契约，保留为独立类型诊断，不混入本次内部清理修复。
