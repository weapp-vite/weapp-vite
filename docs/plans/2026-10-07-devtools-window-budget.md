# IDE 窗口配额与失败清理

本轮使用用户指定的 Stable `2.02.2608070`，继续执行官方版本查询和安装身份核验。版本例外保持 `selected-version-opt-in`，不修改默认官方 Stable 门禁。

## 已确认的问题

受管 journal 原先只拒绝未确认的启动和未完成的关闭。前一个窗口进入 `owned` 后，可以继续登记新窗口，同一任务中没有数量上限。跨 worktree 串行不能约束一个任务内部的窗口累积。

snapshot 启动失败时，窗口清理抛错会跳过文件 watcher 和日志订阅的停止。快照目录的异步删除又在成功前标记 `cleaned`：删除失败后不会重试，并发清理的第二个调用也不会等待第一个完成。

启动日志还有一个误判：所选 IDE 在捕获启动错误后仍可能输出 `simulator launch success`。这条文本不能证明页面已经运行，不能据此过滤前面的启动错误。

## 修复边界

- 在现有 journal 根锁中检查整个任务子树，默认最多一个受管窗口。仅共享宿主、并发会话和窗口生命周期验收显式使用两个窗口，结束后恢复环境；不支持无限配额。
- `begin` 仍表示可能开窗的操作。已经登记的同一项目必须通过既有 endpoint 重连，不能再次 `start`。复用连接不创建新的窗口所有者；未启用受管 journal 的公共 CLI 行为保持原样。
- 启动失败立即停止本任务的 watcher 和日志订阅，再等待迟到桥接及精确窗口清理。窗口回收未确认时保留目录；尚未派发启动或已完成窗口回收时删除本任务快照。
- 清理调用共享一个 Promise，全部调用者等待同一结果。失败清除待处理状态以允许重试，成功后重复清理不再删除文件。
- 日志扫描保留原始启动错误。新的运行仍通过日志 baseline 隔离历史失败，无错误的成功日志继续通过。

不根据进程名或项目路径前缀关闭共享宿主，不删除用户缓存和历史项目。官方实现显示项目窗口关闭后会释放对应 backend/runtime，项目列表主要保存元数据；历史条目数量本身不能证明进程泄漏。

## 冷启动验收补强

`app-lifecycle` 比较三个不同 App 实现，每个 fixture 仍只启动一次。后续验收显式使用原 fixture 产物，由 `onSessionMetadata` 读取启动回执对应的 journal，核对本次调用之后创建的 `owned` 记录、`openedProjectWindow: true`、项目路径与端口。借用既有窗口、旧记录、项目或端口漂移均在握手前失败；回执未执行也不能通过验收。

原生窗口的本次新建证明与现有 `onLaunch` 宿主输入观察器共同验证冷启动，不以新磁盘目录作为冷启动判据。保留单次启动、禁止连接后刷新、禁止 warmup 导航及禁止重导航恢复的约束，不修改页面、AppID、hook/DOM 断言或全量任务清单。依次运行窗口证明的单测、同一 `app-lifecycle` headless 场景和严格真实 IDE 场景；snapshot 原始启动失败仍作为独立证据保留。
