# 原生构建测试的完成观察

Windows Node 24 的完整覆盖率测试在“构建期间收到的变更进入下一次 snapshot”场景中，等待第三份 bundle 时超时，实际观察到两份。测试默认的 `vi.waitFor` 预算为 1 秒，而相邻真实 Vite 构建场景在同轮执行中耗时约 1.3 至 3.1 秒。日志没有记录第三次构建的完整结算，不能仅据此断言 scheduler 丢失事件。

最小调整统一 fixture 的成功与失败条件等待预算为 10 秒，并让该场景复用 `nextBundle(2)`。等待条件满足即返回，不增加固定停顿；仍要求恰好三份 bundle、对应的原生写盘次数，以及首批不包含排队模板、次批包含其最新内容的原断言。生产 scheduler 保持原实现。

另行引入构建结算通知和 waiter 清理协议会扩大测试设施的改动；通过关闭 watcher 等待则会取消尚未执行的批次，无法证明发布完整。当前采用既有条件等待入口，并以新一轮 Windows CI 是否实际完成全部内容断言核验这一诊断。局部通过不能替代该平台结果。

同轮 Windows Node 22 的 classic 回退测试也在默认 1 秒产物轮询处失败。同一测试在 Windows Node 24 通过，而配置写入后立即保存脚本，旧宿主仍可能以旧 define 生成短暂产物。测试现在先有界等待公共 server 的 define 切换到新配置，再立即检查产物确实包含新值。Vite 在新宿主创建完成后才替换公共 server 的配置，这一观察覆盖实际宿主交接，保留自动配置监听及原两次写入顺序，不额外触发 restart。后续 classic 身份、运行时退役、显式重启与新命令恢复断言继续执行。

该 HMR 集成测试文件原已超过 300 行。本次只调整配置重载的完成观察，沿用同一 fixture 和会话中的连续场景以验证命令生命周期；拆分会扩大当前修复并打断连续语义，因此保留现有布局。
