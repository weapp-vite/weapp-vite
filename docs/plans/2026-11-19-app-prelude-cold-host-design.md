# Prelude 多拓扑真实 IDE 验收隔离

全面回归在 Stable 2.02.2609250 中两次复现：inline 模式完成全部运行断言并关闭项目窗口后，default 模式的官方 `project_import` 请求停在 AppID 属性查询，未进入 automator 连接阶段。原生日志已记录前一窗口及 webContents 销毁；界面只剩项目列表。180 秒启动预算耗尽，最终由 runner 正常退出本任务认领的宿主。窗口峰值为一，没有 OOM、并发任务或遗留端口的证据。

直接 Vitest 的快照路径能运行 inline 和 default，但未经过相同的受信项目导入，不能替代受管入口复现，也不能证明官方导入已恢复。

## 方案

沿用 app-lifecycle、auto-routes 的变体任务机制，将 inline、default、legacy-es5-request-runtime、default-request-runtime 分成四个真实 IDE task。每个 task 由既有 runner 取得机器租约和冷宿主关闭权，导入一个拓扑、运行完整用例、关闭项目并退出宿主，核验资源终结后才运行下一项。每个模式内部继续用同一 automator 和 `reLaunch` 覆盖主包及分包页面。

测试文件保留四个原始用例和全部断言，模式选择只决定当前 task 的精确计划。严格 DOM 清单预先声明该模式对应的完整 case；四个 task 的 case 并集必须与源文件清单相等且无重复。headless 保持聚合执行四例，覆盖语义不变。

延长超时不能解决导入无响应；在测试内部重启宿主会分散 runner 的所有权。选择任务隔离，使构建拓扑原本要求的独立冷启动由现有资源生命周期统一保证。官方导入在关窗后的停滞作为环境边界保留证据，不声称修复了 IDE 内部实现。

## 验证与范围

先验证清单与严格 DOM 计划，再运行 headless 四例和真实 IDE 四个变体。四个变体全部通过后，同步干净 main 执行正式完整 IDE 清单。任何未执行或失败 task 均不能计入全面验收通过。

本次只调整 E2E 调度和模式选择，不改产品包。现有 manifest 及其测试超过 300 行，本次保持变体机制相邻放置，避免为四个任务另建一套清单；后续若继续增加变体，再统一抽取任务工厂。

专项结果：headless 聚合四例通过；真实 IDE 四个变体均通过，实际基础库为 3.18.0，每项均完成原生窗口销毁、端口释放和宿主退出核验。这两次筛选运行的严格 runner 按 partial 策略返回非零，结果只作为专项证据，不计作完整验收。独立 task 使 exhaustive 总数从 191 增为 194，原有三个非微信范围项保持原有范围，case 并集不变。
