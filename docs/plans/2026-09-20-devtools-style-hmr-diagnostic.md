## 已证实的宿主缺陷

Stable 中 `AppConfigService.getAppConfig` 使用 `makeSingleton(1000, -1, 100)`。`SingletonTask` 未判断负值，直接以 `this.timeout` 调用 `setTimeout`。Node 与该 IDE 自带 Electron 都把 `-1` 转为约 1 ms 的延迟，而非无限等待。

首个调用直接等待 executor，并发调用等待内部队列。若 executor 尚未结束而定时器先触发，队列收到 `timeout`，但 executor 未取消，首个调用仍可成功。同一配置查询因此出现一个成功、其他失败的结果。

只读加载宿主原始模块，以约 10 ms 完成的配置 executor、相同参数发起三个并发请求，结果如下。负值修正只作用于探针内存中的模块，未改动系统安装。

| 实现 | 超时参数 | 首个请求 | 两个并发请求 |
| --- | --- | --- | --- |
| 原始 | -1 | 成功 | timeout |
| 原始 | 1000 | 成功 | 全部成功 |
| 仅增加负值判断 | -1 | 成功 | 全部成功 |
| 仅增加负值判断 | 1000 | 成功 | 全部成功 |

原始 `transWXSSToJS` 入口的隔离依赖探针进一步确认：另一个同窗口配置请求先进入时，WXSS 请求可因该 timeout 被拒绝，样式编译 executor 的调用次数为 0。增加负值判断后两个请求均成功，样式编译调用次数为 1。

官方 Nightly `2.02.2609182` 的安装包通过腾讯签名与 Apple 公证校验后，仅解包检查。它仍包含相同配置和负超时逻辑；Node 与 Nightly 自带 Electron 的只读探针结果一致。未运行 Nightly 真实模拟器，不能把模块探针写成该版本的 runtime 验收。

## 真实宿主对照

对照使用独立 IDE 副本，同一副本路径、登录配置与测试代码，只切换一个宿主模块的负超时判断。逐归档条目比较确认没有其他模块变化。系统安装未修改；副本在对照结束后恢复原始内容。

Wevu 场景按“修正、原始、修正、原始”顺序运行：修正侧两次通过 7/7 检查点，原始侧两次在首个背景修改处持续透明。这与配置及 WXSS 入口探针相互印证，支持宿主负超时导致样式更新丢失。

原生 TDesign 的对照结果有不同限制：

| 场景 | 宿主模块 | 结果 |
| --- | --- | --- |
| 原有两个用例 | 负超时修正 | 通过 |
| 原有两个用例，连续两轮 | 原始 | 两轮均通过 |
| 同一页面连续八次背景修改 | 原始 | 第五次修改持续透明 |
| 相同八次修改 | 负超时修正 | 全部通过，页面/App 身份保留 |
| 再次恢复原始模块，相同八次修改 | 原始 | 全部通过 |

连续诊断使用八个不同的任意色值，等待页面 WXSS 包含新颜色，再检查真实节点属性、计算样式及页面/App 身份。共享一个 automator 会话，不在每次修改后重启或重新编译。临时压力场景及 CLI 覆盖参数已撤回，不修改默认测试范围。

这些原生结果证明故障可以在连续更新中出现，但反向对照未稳定复现，**尚不能把负超时缺陷认定为原生失败的唯一根因**。修改后的副本也不计入官方 IDE 最终验收。

随后仅对副本的负超时回调增加本地记录，不改变原有拒绝行为：原有绿色背景用例再次失败；在更新后的 WXML 检查点之前约 150 ms，`getAppConfig` 拒绝了三个排队请求。压力场景在此前用例未完成模式恢复后受到影响，其后续失败不作为独立证据。

追加排队请求调用栈后，确认真实宿主中存在 `getAppConfig -> transWXSSToJSLazyload -> transWXSSToJS` 的 WXSS 请求被负超时拒绝。但采集调用栈的那轮原有用例仍通过，所以“出现负超时”不是页面必然失败的充分条件。需要关联被拒绝请求的具体样式文件及同批其他请求结果；不能用时间接近取代完整因果证据。所有本地插桩均已撤回，系统安装始终未修改。

文件级插桩进一步解释了两轮通过结果：`pages/layouts/index.wxss`、`weapp-vite-global.wxss` 请求在配置查询阶段 timeout；当前 `pages/index/index.wxss` 请求成功，编译结果含新绿色，页面也正常。相同记录方式下的八次连续更新全部通过，当前页每次编译结果包含目标颜色，个别其他样式请求仍被拒绝。

上述同步日志轮次尚未捕获“当前页 WXSS 请求被拒绝且无成功结果补足”的完整链条。插桩可能影响调度时序，所以不把插桩侧通过解释为原始宿主已经恢复，不以增加日志作为修复。

## 缓冲日志的文件级证据

随后将日志改为内存收集、500 ms 后批量写入，避免在每次配置查询及编译结束时同步序列化完整结果。保留原始超时逻辑，同一页面连续更新 24 个颜色；第十次更新再次透明。以该次源文件修改为时间原点：

| 相对时间 | 请求或状态 | 结果 |
| --- | --- | --- |
| 0 ms | 更新背景为 `#2c4f72` | 后续已确认 emitted 页面 WXSS 含新颜色 |
| 790 ms | `pages/index/index.wxss` 配置查询 | `timeout`，未进入 WXSS 编译 |
| 791 ms | `weapp-vite-global.wxss` 配置查询 | `timeout`，未进入 WXSS 编译 |
| 861 ms | `pages/layouts/index.wxss` | 编译成功，含 `#2c4f72` |
| 检查点重试耗尽 | 当前页真实背景 | 预期 `rgb(44, 79, 114)`，实际透明 |

该批直到 suite 清理前，没有当前页或 `app.wxss` 的后续成功编译。之前九次连续更新均通过；每次都有当前页或全局更新链成功。原有绿色用例的当前页请求也曾 timeout，但全局及 `app.wxss` 后续成功，页面通过，解释了为何单独统计 timeout 次数不足以判断故障。

宿主热更新调用链与记录一致：WXSS handler 等待 `transWXSSToJS`，从响应中取当前请求文件的 `page`，然后才调用 `updateWxAppCode`。配置查询拒绝会在应用前抛出；其他页面请求返回自己的 `page`，不能替代当前页更新。全局更新链另行获取 `comm` 并更新关联页面，所以全局成功时可以补足当前页独立请求的失败。

保留相同缓冲记录与测试，仅增加负超时判断，再跑原有两个用例及同样 24 次连续更新，全部通过，共 35 个 DOM 检查点，页面/App 身份保持。该轮记录到 25 次当前页样式热更新编译成功，配置请求失败为 0。它与失败轮次的文件级证据相互印证，定位到宿主配置查询丢弃并发请求的缺陷；副本结果仍不算官方 IDE 最终验收。

最后恢复原始超时逻辑，保留同样缓冲记录与测试，第二十二次更新 `#508bc6` 时再次持续透明。当前页及全局样式请求分别在源文件修改后 776 ms、778 ms 被配置 timeout 拒绝；849 ms 时只有 `pages/layouts/index.wxss` 编译成功，没有当前页或 `app.wxss` 的后续成功结果。原有两个用例均通过，压力用例失败。至此形成“原始失败、仅修正负超时通过、恢复原始再次失败”的同场景对照，两次失败均有相同文件级链条。

所有临时测试及副本插桩在诊断后撤回，系统安装未修改。原生 FSEvents 探针也再次收到了全部三次修改事件；当前失败不是此前系统文件事件丢失的延续。

## 继续定位的边界

当前已定位到宿主负超时造成原生样式请求丢失的完整路径。仓库源码无法修正官方 IDE 内部 singleton；修改独立副本只用于根因对照，不作为产品修复或最终通过证据。需在未修改的官方宿主中完成稳定复验后，才能更新验收结论。

- 保留真实颜色、交互状态和页面/App 身份断言，不增加 skip 或超时，不通过重编译页面掩盖失败。
- 构建文件由 Vite/Rolldown 持久化，不添加手动重写 WXSS、重复触碰文件或重试到成功的补偿逻辑。
- 登录、服务端口和日志订阅失败单独记为基础设施故障，不作为宿主运行时契约。
- 当前本机 FSEvents 已恢复，不需要关闭 SIP 或继续重启系统服务。
- 若修改仓库 runtime 行为，继续补充对应 mpcore 覆盖并重建包；诊断文档本身不改变 runtime、公开 API 或发布版本。
