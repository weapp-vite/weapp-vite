# HMR 完整重载后复用受管 IDE 会话

## 失败复现

严格 IDE exhaustive 在 `app-vue-hmr-alias` 完成 initial checkpoint 后失败。完整重载恢复先调用 `disconnect()`，随后再次调用 `launchAutomator()`；前者只释放 WebSocket，原项目窗口和 journal owner 仍然有效。后者却创建新的启动意图、申请新端口并执行 `agent start`。

本轮新启动回执未通过校验，启动意图保持 `unconfirmed`。原 owner 的窗口后来完成销毁，但未知意图仍使清理失败，机器租约因此保留。原始回执未完整保存在测试报告中，不能将其推断为某一种复用或端口冲突响应，也不能把端口为空、窗口采样为零当作意图已经确认。

同型调用还存在于 classic HMR 和 issue #1134 的 batch、topology 场景。首次启动失败与本次重连错误分别记录；修复重连不能覆盖此前冷启动失败。

## 修复边界

使用独立的 `reconnectAutomator()` 复用已登记的项目、端口、安装身份及关闭 owner。重连只更换协议连接，恢复版本检查、日志订阅和现有会话增强，不启动 IDE、不创建新的项目 journal，也不隐式导航或编译。

新的连接必须通过当前 journal、宿主及端口身份核验；失败保留原 owner，交由原来的幂等清理流程收尾。多次重连共用同一个关闭 owner。未知或已释放的会话不能重连，不回退到重新启动。

关闭原窗口后再启动会改变完整重载的观察对象；接受不匹配的启动回执会削弱所有权保护。这两条路径均不采用。

headless 没有可分离的 IDE 连接，继续关闭旧 VM 并从新构建产物创建 VM。已有页面、状态、checkpoint 和查询参数断言保持完整，DevTools 与 headless 仍验证各自对应的运行结果。

## 验证与交付

- 纯 mock 回归覆盖：重连不启动项目、身份不符时拒绝、失败不丢失原 owner、连续重连只释放一次、日志和会话增强恢复。
- 串行验证四个真实 IDE 场景，确认原项目窗口及端口身份跨重连保持一致，原有 checkpoint 全部完成。
- 对 provider-compatible 场景复跑 headless，确认 VM 重建和原有行为断言未改变。
- 保留首次失败与资源记录；恢复受阻租约必须取得独立、明确的无活资源证据，不能补造未知回执或删除全局状态。
- 重连修复只涉及测试连接基础设施；新增的显式资源终结 API 单独添加中文 changeset 和类型契约覆盖。

`automator.ts` 和既有 IDE 场景已超过 300 行。新增重连协议和单测放入独立 helper，主文件仅接入现有增强，避免继续把所有权校验堆入主文件；场景只替换重连调用。

## 未确认启动意图的显式恢复

普通清理继续拒绝 `unconfirmed`。不能通过让通用 machine recovery 回调直接返回成功来跳过项目领域检查，也不能凭空闲端口推断启动命令没有开窗。

显式恢复先保存旧任务租约、journal 和报告的精确快照，再接管全部已停止且封存的 scope。Computer Use 确认同安装只有项目列表后，在恢复租约内正常退出宿主。领域 API 重新核验安装身份、登记 owner 已退出、所选安装全部进程已退出及相关端口关闭，才记录独立的资源终结原因，并保留原状态和错误。

终结原因不代表启动成功或窗口 ownership 曾被确认。重新打开同一安装、确认新宿主状态和全部 journal 的领域终态后，才能完成 scope 并释放恢复租约。原 suite、checkpoint 和首次失败报告不做任何改写。

领域恢复操作在第一次异步等待前登记到当前恢复 scope。回调若漏等候该操作，租约守卫会等待在途操作结束，然后保留未完成 scope 并报错；不能在 journal 写入尚未完成时释放租约。普通租约、伪造 scope、已结束回调和另一个模块实例均不能取得此权限。

本次安装退出证明仅支持已验证的 macOS 能力。`ps` 只提供 PID、启动时间和僵尸状态；实际可执行路径由系统 JXA 调用内核 `proc_pidpath` 读取，不涉及 UI。对仍运行但映像已从磁盘删除的进程，检查完整的 `lsof` program-text 映像清单。权限不足、清单不完整、身份变化或持续出现无法核验的新进程均拒绝恢复；其他平台保留原记录，不以进程名降级判断。

## 直接运行 Vitest 的资源边界

直接调用 IDE Vitest 配置时，原 global setup 只持有根机器租约。worker 独立创建的 journal 没有绑定机器 child scope；若 worker 清理未知窗口失败，根租约仍可能释放，下一个文件或命令便可能启动更多窗口。

global setup 现在先创建 journal 和绑定 cleanupKey 的 child scope，再发布给预检与 worker。teardown 使用仍有效的父凭证清理，兼容源码与发布包的独立异步上下文；只有领域清理完成才能完成 scope。清理失败时保留未完成 scope，阻止根租约释放。直接入口与聚合入口都保持相同约束，headless 也按同一流程完成空 journal 清理。

退出宿主后的 UI 查询本身可能重新激活应用，因此退出证据使用不启动应用的清单和内核进程核验。若正常退出完成后恢复进程中止，下一次只能精确接管已停止的快照，重新证明安装完全退出后续行；报告保留每次尝试，区分退出与重开所在的租约，不合并成一次无中断恢复。

## 局部回归暴露的后续问题

批量四文件更新的真实 IDE 场景完成了两个 case、九个 checkpoint；三个 provider-compatible headless 场景完成七个 case、三十三个 checkpoint。这些都是工作区未提交状态的局部证据，不计作最终同提交验收。

alias 的 app/layout 更新已能重连原窗口。页面增量补丁发布并消费后，`getCurrentPages()` 返回的 facade 仍包含旧值；同次失败采集的 `Page.data()` 与实际元素文本均已包含新值，bridge 实例的 data 与 snapshot 也已更新。问题位于等待器的观察面，不能据此修改 wevu 数据提交行为。就绪判断应同时核对真实页面数据、精确元素文本、路由和可见性；facade 只用于失败对照，五个 DOM checkpoint 保持完整。

修后 alias 真实 IDE 完成一个 case、五个 checkpoint，原窗口复用期间受管窗口峰值为一，结束后 journal 与端口均释放。对应 mpcore 连续数据更新场景的 unit 和浏览器各两个测试通过；旧 marker 留在非目标节点，确保断言确实读取指定节点的新文本。wevu 的独立宿主提交测试也通过，未修改其运行时代码。

classic 的三个入口均在新 native bundle 编译及 AppService 自动重载之前执行了带参数导航；重载后的页面 ID 改变、状态重置且 query 为空。修复在协议重连后先观察新 marker 与重置状态，再执行原有的一次导航，不增加导航、重试或固定等待。修后真实 IDE 与 headless 均完成三个 case、十二个 checkpoint，真实窗口逐个释放且端口关闭。这仍是未提交工作区的局部验证，不能代替最终同提交回归。

另外确认 automator 的正常导航就绪分支只比对路径，相同路径但旧 query 的页面会提前返回。修复核对请求中显式携带的参数，保留宿主额外参数和实际返回值，不补造 query，也不追加导航。该行为独立添加中文 changeset。`MiniProgram.ts` 已超过 300 行，比较规则拆到 `navigation/query.ts`，回归测试单独成文件。

topology 在启动阶段耗尽预算后，仍以约 1.3 秒剩余时间派发第三次启动。取消早于完整回执，形成未知启动；随后 teardown 因会话尚未赋值而跳过关窗，直接删除临时项目。晚到的窗口因此显示工作目录无法解析。修复需要同时约束启动与目录寿命：必经连接稳定阶段的预算不足时不创建新启动意图；停止 watcher、会话和 journal 资源后才删除临时项目，任何清理失败均保留目录。原失败与未知记录继续保存，恢复不能改写通过状态。

后续运行将 topology 失败缩小到第一次样式更新后的导航。classic 和 stateful 两种模式均有重连早于 AppService 重建的原生日志。更新前给当前 App 写入唯一、不可枚举的标记，并通过另一次协议读取确认其持久性；重连后只读等待有效的新 App、当前页面及可见原生根节点，再执行原有导航。查询回调重新核对 App 和页面身份，防止跨重载返回的旧尺寸提前通过。标记不写入 storage，不修改构建产物，也不承担样式验收；原有精确样式、组件、路由及撤销断言全部保留。

该门禁的十四项单测包含旧 App、无 App、无页面、无可见节点、协议失败和回调期间对象替换等边界。修后 topology 的 headless 和真实 IDE 均完成两个 case、十二个 checkpoint，所有受管启动记录及端口完成释放。结合其余局部回归，当前仍须提交后重新执行完整验收；官方宿主自身的冷启动失败另存证据，不能由这些通过结果覆盖。
