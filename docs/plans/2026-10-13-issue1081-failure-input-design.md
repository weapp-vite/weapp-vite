# #1081 故障输入的原子发布

Ubuntu headless 首轮的延迟编译事务场景在故障检查点观察到客户端版本从 3 变为 4。原日志显示，CSS Modules 的 revision 160 已确认完成；随后 revision 161 捕获的 `src/batch.ts` 为 0 字节，经过准备、样式提交、发布及确认。第二次文件事件才读取到完整的 `BATCH_FAIL` 输入并报错。因此新增版本来自原地写入时的合法空文件，不是失败的编译事务。

场景要求一次保存发布完整的故障输入，与已有正常保存的 `.pending → rename` 约定一致。继续原地写入可能混入另一个合法事务；用等待、重试或放宽版本断言会隐藏输入差异。选择在测试内收敛 `saveSource(file, content)`，正常脚本、CSS Modules 和故障输入都先写同目录临时文件，再使用现有 `renameAtomicFile` 发布。

不修改生产 watcher、编译器、交付、预算或原断言，不过滤空源码；空文件仍是合法产品输入。测试仍须证明编译持有期间旧 DOM 保持、最新输入与样式同批生效、失败后版本和样式保持、后续恢复成功且页面状态保留。

验证复用原 provider-compatible 场景及原六个 DOM 检查点，先执行最小 headless，再跟踪三平台完整 CI。真实 Stable 的最终验收限制继续保留。该变更仅修正测试输入发布方式，不需要行为 changeset。
