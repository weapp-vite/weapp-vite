# Windows classic IDE 配置锁竞争修复

最新主线的 Windows Node 22 覆盖率检查在两个并发锁测试中失败，原生目录重命名返回 `EPERM`，而同一提交的 Ubuntu 测试通过。代码已将 `EPERM` 识别为 Windows 目录冲突，但随后回读 guard 不存在时又立即抛错；持锁者在重命名失败与回读之间释放 guard，就会进入这条提前退出路径。远端日志未记录底层删除时序，竞态通过本地确定性故障注入单独复现。

修复复用现有 1 秒竞争预算与轮询路径：回读无 owner 时重新尝试原子发布候选，只有重命名成功才进入事务。持续 `EPERM` 在预算耗尽后仍原样抛出权限错误。活进程、未知格式、死亡 owner 的核验，以及只删除观察到的 token、保留后来 owner 的规则继续生效。

额外预读 guard 仍存在检查与重命名之间的竞态；整体更换锁协议会扩大这次平台修复的范围。因此采用现有状态机内的有界重试，不增加删除权限或其他发布路径。

回归覆盖冲突返回前另一持锁者已完成释放、持续权限失败保留原错误且不执行事务，并复核原有并发、两个回收者及迟到释放者场景。验证范围包括相关锁、journal、恢复与 prepare 测试、包级类型、公开类型和重建产物；后续仍须完成新提交的原生 Windows CI 与完整 E2E。新提交重新冻结清单，旧提交已完成的结果保留原身份。
