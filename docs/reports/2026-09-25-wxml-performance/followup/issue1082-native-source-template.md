## 对照与结果

首先把已有 Wevu 模板往返场景的源文件保存方式，从原子 rename 替换改为普通 `fs.writeFile` 原文件内写入；首次新增节点、计数、输入、路由及恢复断言全部保留。headless 6/6 通过，真实 IDE 仍在首次编辑失败（2/6）：输出 marker 已就绪，但 `.template-cycle` 期望 1、实际 0。因此原子替换保存不是该现象的必要条件。

随后建立一个只包含 `App({})` 和原生 Page 的源码项目。`miniprogramRoot` 指向源码目录，项目只有 App 配置、App 脚本和页面 WXML/JS/JSON，没有构建命令、开发服务器、Vite/Rolldown、Wevu 或 stateful 客户端。真实 AppID 与热重载设置沿用现有 fixture，页面条件同步为唯一原生路由。测试直接编辑实际源 WXML，不生成或手写构建产物。

## 真实 UI 观察

在另一次原生源码运行中，原 DOM 断言已经失败后，临时观察逻辑保留现场，等待读取结束再原样抛出失败；没有重试断言到通过。Computer Use 通过原生微信开发者工具应用读取 AX：当前页面为 `pages/native/index`，计数 2、`held-input` 和原 marker 在，新增模板节点不在。直接点击 UI 中原来的加号按钮后，计数变成 3，输入保留，新增节点仍不在。与此同时实际源码含 `TEMPLATE-CYCLE-0`。因此这一失败并非仅为 automator 选择器误报。

另一次测试结束、断开连接并恢复源码以后，再次从外部编辑源 WXML，Computer Use 看到了不同的新 marker，点击也能正常递增。这个后续更新成功不能替代首次失败，也不足以证明断开 automator 是使其成功的原因：恢复事件、缓存状态和更新顺序都已不同。

该对照表明构建器、Wevu、stateful 客户端均不是复现所必需的条件；项目仍通过仓库的 automator bridge 启动，尚未排除 bridge 与 IDE 的交互，也没有证明唯一内部缓存修复点。已有纯原生 classic、可见旧模板工厂和只读缓存调查继续保留。
