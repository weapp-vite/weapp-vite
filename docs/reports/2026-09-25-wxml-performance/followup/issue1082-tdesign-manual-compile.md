# PR #1086：一次 IDE 编译后的 TDesign 运行时验证

用户报告的“点一下 IDE 编译后恢复”已在真实普通窗口复现。当前产品为 `bad3afc8702b6606f6de8fd861d0c305f487d2a7`，完整默认 layout 和 TDesign 组件均保留。该结果更正了此前仅根据自动启动超时作出的过宽判断：自动启动失败，不等于相同产物无法运行；它仍不构成自动启动门禁通过。

## 相同产物下的一次编译

新临时项目经正常 Vite/Rolldown 开发流程输出，再由 IDE 自带 CLI 打开。首次页面空白，出现“模拟器长时间没有响应”；Console 确认实际基础库 3.17.3，App 已启动，但页面栈为空。

在开发服务持续运行时，只执行一次 IDE 工具菜单的“编译”。随后 App 启动标记变化，页面栈出现 `pages/index/index`，完整 TDesign 首页显示，真实点击能切换暗色。未改 SDK 版本、源码、layout 或 HMR 接受规则，没有手动写产物或调用客户端 apply。

编译前、点击前、点击后和页面恢复后，四次快照中 1212 个产物文件的字节 hash、大小和 mtime 完全相同。两个项目配置中所记录的 `libVersion`、`miniprogramRoot`、`setting` 字段也一致。这证明本次恢复不依赖新的磁盘产物；尚不能确定是宿主编译缓存、文件索引还是初始化时序中的单一原因。

## 必须保留的差异与失败

- 脚本 HMR 后，App 上下文和主 Console 中 `getCurrentPages()[0].data.mode` 停在旧的 dark；可见文字和原生样式查询却继续正确变化。11 个阶段中有 5 次读值与可见模式不同，原值完整保留。不能据此声称跨上下文数据一致性已通过，也尚未证明差异属于框架还是宿主上下文投影。
- 临时把官方 `miniProgram.compile()` 放到日志订阅前，接口明确返回 `unimplemented`，0 DOM。没有把不支持当作成功，启动器源码已恢复。
- 原 TDesign 两用例不改源码或断言，在自动化精简窗口中执行一次菜单编译，仍在读取当前页时超时，0 DOM。该次窗口模式、连接状态和编译时机与普通窗口不同，不能单独归因于精简模式。
- 因而上表是 Computer Use 工作流的可见交互及 SDK 查询记录，**不是原自动化 suite 的 11/11 通过结果**。自动首次启动、数据读值差异和其他未完成验收继续跟踪。
- 开发进程按诊断期限正常停止后的 `ERR_CONNECTION_REFUSED` 单列为清理后的观察，不将其删除，也不据此反推此前 HMR 失败。
