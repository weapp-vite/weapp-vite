# 小程序平台现状与 weapp-vite 投入建议

调研日期：2026-11-04（Asia/Shanghai）。本文记录当日能核实的公开信息，用于讨论多平台适配投入；平台开放范围、准入要求和运行能力以接入时的官方规则为准。

## 结论

微信之外，支付宝、抖音、小红书、快手都有官方公开的小程序经营案例。其中，小红书是相对较新的重点关注对象，近期开发文档和已上线案例的证据较完整。百度智能小程序在 2026 年仍有运营公告；京东、淘宝的官方开发入口仍在，但本次没有核实到同等充分的近期经营案例。

对 weapp-vite，建议优先做稳微信、支付宝、抖音、小红书，再评估快手；百度、京东结合实际客户需求维护。鸿蒙元服务应单独评估技术路线，钉钉、飞书则围绕企业应用需求考虑。这是工程投入建议，不是市场份额或增长率排名，也不代表新增平台的交付承诺。

## 调研范围与证据边界

本次主要关注中国大陆平台面向第三方开发者的小程序，不以小游戏、普通 H5 页面、平台自营服务或单个商家店铺代替独立小程序平台。

判断时分别查看官方开发入口、近期公告或维护记录，以及具名的已上线案例：

- 官方文档在线，只能证明开发入口仍可访问，不能单独证明商业活跃度。
- 官方展示具名案例，可以支持“存在实际业务应用”的判断；本次未逐一在对应 App 内打开案例或完成交易。
- 未标注独立日期的案例，不作为 2026 年新增业务或实时经营规模的证据。
- 公告日期与查询日期分别记录，不把网页抓取时间、HTTP 更新时间当成业务发布日期。
- 没查到近期案例，不等于平台停运。维护优先级需要结合用户需求、适配成本和可用的 runtime 验证条件决定。

本次未做跨平台用户量、交易额或开发者数量的统一口径统计，也未执行目标平台的编译、真机或 runtime 验收。

## 微信与 QQ：互通范围不能等同于平台全面合并

2025-05-06 的《中国经营报》报道《微信与 QQ 实现“小程序”互通》提到，QQ 9.1.70 开始小范围测试运行微信小程序。报道引用腾讯回应，目标是让开发者“一次开发、双端部署”，减少重复开发和运营投入。参见[报道转载全文](https://www.toutiao.com/article/7501219235004465675/)。

截至本次查询，[QQ 开放平台](https://q.qq.com/)仍列有“QQ 小程序/小游戏”入口。本文将上述报道描述为“QQ 测试接入微信小程序、推动双端互通”；本次未独立核实当前全面开放范围，也不据此认定原 QQ 平台全面停止，或两端所有 API、登录、支付、审核规则都已经一致。

对框架维护而言，不宜仅凭“QQ 也是一个宿主”就决定新增独立编译目标。应先核对当前互通范围、发布路径和所需的 QQ 专属能力，再判断是否需要单独适配。

### 为什么重点关注小红书

小红书已经具备独立的小程序开发与发布体系。官方介绍明确说明，需要通过小红书开发者工具开发；已有 Taro、uni 等框架项目可以通过对应适配方式迁移，不能把外链微信小程序视为完成接入。

除具名案例外，本次还核实了以下维护记录：

- [2.0 架构迁移通知](https://miniapp.xiaohongshu.com/doc/DC702500)：页面标注于 2025-02-14 更新，说明 2.0 架构推全及老架构逐步停止维护。
- [基础库更新日志](https://miniapp.xiaohongshu.com/doc/DC600298)：有 2026-04-03 的 3.151.0 版本记录。
- [开发者工具更新日志](https://miniapp.xiaohongshu.com/doc/DC999582)：有 2026-04-07 的 2.9.1 版本记录。

这些信息支持持续维护 `xhs` 目标的价值判断。具体项目仍需核对主体资质、开放类目、支付能力和发布审核，不能由“框架可以生成代码”推导出“任意业务都能上线”。

### 为什么把快手作为新增候选

快手官方案例覆盖旅行、本地生活、文学和课程，说明其小程序用途包含实际服务与内容经营。[官方接入指引](https://open.kuaishou.com/docs/introduction/quickStartGuide/quickStart.html)也提供创建和接入流程。

在决定新增目标前，应先核对开放类目、账号准入、模板语法、脚本模块、项目配置、API 与生命周期差异，再确认开发工具及 runtime 验证路径。已有案例是启动调研的依据，不能替代兼容性验证。

## 鸿蒙元服务：单独评估技术路线

[华为官方元服务介绍](https://developer.huawei.com/consumer/cn/fa/)将其定义为具有独立入口、免安装、能够独立实现业务闭环的应用形态。

它值得作为轻服务方向关注，但属于 HarmonyOS 应用体系。开发模型、UI、分发和验证环境需要独立评估，不能直接假设增加一组小程序文件后缀与 API 别名就能接入。本文未验证其与 weapp-vite 的编译或运行兼容性。

## 与当前 weapp-vite 能力的对应关系

仓库当前的小程序目标由 [`@weapp-core/shared/src/platforms/descriptors.ts`](../../@weapp-core/shared/src/platforms/descriptors.ts)统一描述，公开用法见[多平台构建指南](../../website/guide/multi-platform.md)。

| 小程序目标 | 标识 | 本次建议 |
| --- | --- | --- |
| 微信 | `weapp` | 保持核心目标及真实 runtime 验证 |
| 支付宝 | `alipay` | 优先完善实际业务所需兼容性与验证 |
| 抖音 | `tt` | 优先完善实际业务所需兼容性与验证 |
| 小红书 | `xhs` | 持续维护，跟进基础库、开发工具和开放能力变化 |
| 百度 | `swan` | 结合搜索获客与存量客户需求维护 |
| 京东 | `jd` | 结合京东生态业务需求维护 |

当前指南将多平台能力标为 experimental，且各端自动化验证条件不同。此处列出目标表示仓库已有对应构建描述，不代表全部宿主能力一致或都已经具备同等 runtime 验证。Web 是单独的联调目标，不计为一个小程序平台。

快手、淘宝、钉钉、飞书、独立 QQ 目标和鸿蒙元服务不在上述六个小程序目标中。本文的调研建议不会自动扩大当前支持范围。

## 后续复核

下一次决定新增平台或调整维护优先级时，重新检查官方公告、开放类目、具名案例和实际接入需求。需要投入实现时，再建立最小 fixture 并验证目标宿主的可观察行为。

微信与 QQ 的互通范围、小红书开放类目与架构、快手准入及验证条件，是需要优先复核的项目。本文作为 2026-11-04 的调研快照保留，不替代持续更新的接入指南。
