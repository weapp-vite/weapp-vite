# Test Audit

先读改动路径的 `AGENTS.md` 和[文档与测试审查](../../../CONTRIBUTING.md#文档与测试审查)。默认从当前 diff、生产调用边界及相邻用例开始。

## 新增时

- 先写清可观察行为和能击穿它的回归。沿生产入口找已有用例，能扩展原断言或 fixture 就在那里验证。只有出现独立缺口才新增用例。
- 用稳定的输出、状态、错误或时序作证。以真实调用方和实现为主，测试替身提供外部输入或故障。仅为了观察私有调用需要新增 export、flag 或包装层时，重新选择验证边界。
- Bug 回归优先用同一场景验证修复前按预期失败、修复后通过。无法复现时记录证据缺口。

## 合并或删除时

- 找到待删用例保护的失败，核对保留用例的输入、依赖、执行层、断言和 CI 入口。给出保留的用例路径及它怎样捕获同一失败。结合相关提交或 Issue 判断覆盖起因，证据不足就保留。
- 参数化时保留原来的 fixture、错误形态和关键结果。覆盖率用来定位缺口。对比分支位置之后，还要核对失败语义。例如登录失效和清理异常都可能记录为 `blocked`，要分别断言后续目标是继续还是停止。
- 优先把纯逻辑验证放在单测，共享真实场景的 fixture 和断言。类型契约、构建产物、headless 与真实 DevTools 各自保留需要在该层才能观察到的证据。触及 IDE 场景时，按[真实运行时验收](../../../skills/weapp-devtools-e2e-best-practices/SKILL.md)核对 `mpcore` parity、机器租约和串行要求。

## 验证与交付

- 先跑能覆盖变更的最小入口。涉及 E2E 用例或文件去留时，对照 suite 清单与 CI 选中范围，核对覆盖仍会被实际执行。
- 合并前后用相同输入对照。当层级看起来相同但失败语义有争议时，在隔离副本中模拟该回归，验证保留的断言会失败。
- 在现有 PR 描述或任务回复里写清新增的独立行为、合并后负责的用例、实际验证结果及缺口。用独立行为和失败证据决定去留。
